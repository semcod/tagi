# tagi

`tagi` to paczka Python i narzędzie CLI do **orkiestracji wysyłek zmian Git**, a nie zamiennik komendy `git`. Projekt analizuje nie wysłane pliki, grupuje je w sensowne paczki oznaczone hashtagami i pomaga użytkownikowi zdecydować, które zmiany wysłać najpierw. Wykonanie właściwych operacji nadal należy do `git`, a przy integracji z hostingiem również do `gh` i `glab`.[^1][^2][^3][^4]

## Cel projektu

Celem `tagi` jest uporządkowanie lokalnych zmian przed commitem i pushem. Narzędzie ma wykrywać pliki ze stanu repozytorium, przypisywać im tagi heurystyczne, budować paczki wysyłkowe i dopiero na końcu uruchamiać przewidywalny workflow oparty o istniejące narzędzia Git.[^5][^1]

Najważniejsze założenia:

- `tagi` **nie zastępuje** `git status`, `git add`, `git commit` ani `git push`.[^2][^1]
- `tagi` działa jako warstwa planowania i orkiestracji nad Gitem.[^1][^5]
- Integracje z GitHub i GitLab powinny wykorzystywać istniejące CLI i mechanizmy auth, zamiast implementować wszystko od zera.[^3][^4][^6][^7]
- Opisy commitów i PR-ów mogą być ulepszane przez warstwę LLM, ale logika tagowania i decyzji powinna pozostać deterministyczna.[^8]


## Jak powinien działać

Podstawowy przepływ pracy powinien wyglądać tak:

1. `tagi scan` odczytuje stan repozytorium przez `git status --porcelain` i zbiera listę plików do analizy.[^2][^1]
2. Silnik heurystyk oblicza metryki zmian, takie jak wielkość diffu, typ pliku, nowość pliku, potencjalne ryzyko i możliwe zależności.[^1]
3. `tagi` przypisuje plikom i grupom hashtagowe kategorie, np. `#small`, `#new`, `#deps`, `#docs`, `#tests`, `#risky`.[^5]
4. Użytkownik wybiera interesującą go paczkę lub tag w shellu.[^5]
5. `tagi` pokazuje plan wykonania, proponuje komunikat commita i dopiero po potwierdzeniu uruchamia komendy `git` oraz opcjonalnie `gh` albo `glab`.[^4][^3]

To podejście utrzymuje prosty model mentalny: Git jest silnikiem wykonawczym, a `tagi` jest warstwą decyzyjną i organizacyjną.[^2][^1]

## Główne przypadki użycia

`tagi` powinien wspierać przede wszystkim:

- wybór małych, bezpiecznych paczek zmian do szybkiego wysłania,
- oddzielanie zmian istotnych od pobocznych,
- grupowanie plików po obszarach odpowiedzialności, typie zmian i ryzyku,
- przygotowanie sensownego opisu commita,
- wykonanie sekwencji stage → commit → push po zatwierdzeniu planu przez użytkownika.[^3][^4][^5]

Przykładowe tagi:


| Tag | Znaczenie |
| :-- | :-- |
| `#small` | mały diff, mała liczba plików |
| `#large` | duży zakres zmian |
| `#new` | nowe pliki |
| `#deps` | zależności, lockfile, CI, Docker |
| `#docs` | dokumentacja i README |
| `#tests` | testy |
| `#config` | konfiguracja projektu |
| `#risky` | pliki centralne, auth, migracje, infra |
| `#refactor` | zmiany strukturalne bez nowej funkcji |
| `#feature` | nowy kod funkcjonalny |

## Architektura pakietu

Najbardziej naturalna architektura to modularna paczka Python z wyraźnym podziałem odpowiedzialności:

```text
src/tagi/
  cli.py
  config.py
  models/
    change.py
    group.py
    plan.py
  scanner/
    status.py
    diff.py
    files.py
  heuristics/
    tags.py
    scoring.py
    rules.py
  planner/
    grouper.py
    selector.py
    preview.py
  composer/
    commit_message.py
    summary.py
  executor/
    git.py
    publish.py
  providers/
    base.py
    github.py
    gitlab.py
  llm/
    llx_adapter.py
```


### Warstwy systemu

- `scanner` odpowiada za odczyt stanu repo i surowych informacji o zmianach.[^1]
- `heuristics` przetwarza dane wejściowe na tagi, score i ocenę ryzyka.[^5]
- `planner` buduje paczki wysyłkowe i prezentuje możliwe scenariusze działania.[^5]
- `composer` przygotowuje opis commita, changelog i dane wejściowe dla warstwy LLM.[^8]
- `executor` uruchamia realne komendy `git`, a nie ich lokalną imitację.[^2][^1]
- `providers` obsługują integrację z hostingiem GitHub/GitLab oraz serwerami self-managed.[^4][^3]
- `llm` jest opcjonalnym rozszerzeniem odpowiedzialnym za poprawę stylu komunikatów.[^8]


## Proponowane komendy CLI

Zestaw komend powinien odzwierciedlać rolę orkiestratora, a nie kopii Gita:

```bash
tagi scan
tagi list
tagi inspect #small
tagi draft #small
tagi send #small
tagi publish #small
```

Znaczenie komend:

- `tagi scan` — analiza bieżących zmian w repozytorium.[^1]
- `tagi list` — pokazanie dostępnych grup i hashtagów.[^5]
- `tagi inspect <tag>` — podgląd plików, ryzyka i uzasadnienia dla danej paczki.[^5]
- `tagi draft <tag>` — przygotowanie opisu commita i planu wysyłki.[^8]
- `tagi send <tag>` — staging, commit i opcjonalny push po potwierdzeniu.[^3][^4]
- `tagi publish <tag>` — rozszerzenie o działania na providerze, np. draft PR albo MR.[^4][^3]


## Integracja z GitHub i GitLab

Przy integracji z platformami zdalnymi najlepiej oprzeć się na istniejących CLI.

### GitHub

GitHub CLI wspiera `gh auth login`, `gh auth token` oraz zmienne środowiskowe `GH_TOKEN` i `GITHUB_TOKEN`, więc `tagi` może korzystać z istniejącej autoryzacji zamiast implementować własny pełny flow logowania.[^6][^9][^3]

Przykładowy model:

- `tagi auth github` sprawdza, czy `gh` jest zalogowane.[^3]
- `tagi` może odczytać token przez `gh auth token`, jeśli użytkownik wyrazi na to zgodę.[^6]
- operacje push i PR mogą być wykonywane przez `git` i `gh`, bez przejmowania odpowiedzialności za cały mechanizm poświadczeń.[^9][^3]


### GitLab

GitLab CLI wspiera `glab auth login`, tokeny przekazywane przez stdin, niestandardowe hostname oraz tworzenie tokenów, więc dobrze nadaje się do obsługi GitLab.com oraz instancji self-managed.[^7][^10][^4]

Przykładowy model:

- `tagi auth gitlab` sprawdza sesję `glab` i skonfigurowany host.[^4]
- `tagi` może używać `glab` do autoryzacji i działań na merge requestach.[^7][^4]
- wsparcie dla instancji firmowych powinno być oparte o konfigurację hosta, a nie twarde założenia o `gitlab.com`.[^10]


## Warstwa heurystyk

Logika tagowania powinna być jawna, przewidywalna i konfigurowalna. Dzięki temu użytkownik widzi, dlaczego plik wylądował w grupie `#small` albo `#risky`, bez zgadywania, co zrobił model.[^5]

Przykładowe sygnały heurystyczne:

- liczba zmienionych linii,
- liczba zmienionych plików,
- rodzaj operacji: nowy plik, usunięcie, rename,
- lokalizacja pliku w projekcie,
- rozszerzenie pliku,
- obecność lockfile, migracji, konfiguracji CI,
- wpływ na centralne moduły, auth lub infrastrukturę.

Warto też wspierać lokalny plik konfiguracyjny, np. `tagi.toml`, w którym użytkownik może dopisać własne reguły mapujące ścieżki i wzorce na tagi.

## Opisy commitów i warstwa LLM

Paczka `llx` na PyPI może być użyta jako opcjonalna warstwa do ulepszania komunikatów, ponieważ jest przeznaczona do analizy codebase i doboru modelu LLM dla zadania.[^8]

Dobry model działania jest dwuetapowy:

1. heurystyki budują surowy opis oparty o tagi, pliki i typ zmian,
2. `llx` poprawia styl, skraca lub uczytelnia komunikat commita i opis PR/MR.[^8]

Dzięki temu LLM nie decyduje, *co* ma zostać wysłane, tylko pomaga opisać to, co zostało już wybrane przez deterministyczne reguły.[^8]

## Technologie i zależności

Poniższy zestaw bibliotek dobrze pasuje do pierwszej wersji pakietu:


| Biblioteka | Rola |
| :-- | :-- |
| `typer` lub `click` | interfejs CLI |
| `rich` | czytelny output w terminalu |
| `GitPython` lub `subprocess` | operacje na repozytorium |
| `pydantic` | modele danych i konfiguracja |
| `tomli` lub `tomllib` | obsługa `tagi.toml` |
| `httpx` | integracje HTTP/API |
| `keyring` | lokalne przechowywanie sekretów |
| `pathspec` | obsługa wzorców i `.gitignore` |
| `networkx` | analiza zależności między plikami, opcjonalnie |
| `llx` | poprawa opisów commitów i PR/MR |

Preferowane jest użycie `subprocess` do wywołań `git`, `gh` i `glab`, ponieważ pozwala zachować przewidywalność i zgodność z już zainstalowanymi narzędziami użytkownika.[^3][^4][^1]

## Minimalne MVP

Pierwsza wersja pakietu powinna być mała i praktyczna.

Zakres MVP:

- analiza `git status --porcelain`,
- podstawowe tagi: `#small`, `#new`, `#deps`, `#docs`, `#tests`, `#risky`,
- listing paczek zmian,
- podgląd planu wysyłki,
- commit message draft,
- tryb `--dry-run` dla pełnego bezpieczeństwa.[^1][^5]

Przykładowy scenariusz MVP:

```bash
tagi scan
tagi list
tagi inspect #small
tagi draft #small
tagi send #small --dry-run
```


## Zasady projektowe

Projekt powinien trzymać się kilku prostych zasad:

- jawność przed magią,
- potwierdzenie przed wykonaniem operacji modyfikujących repo,
- brak ukrywania realnych komend Git,
- deterministyczne tagowanie jako domyślny mechanizm,
- LLM jako opcjonalne ulepszenie, nie rdzeń logiki,
- prosty model integracji z providerami przez `gh` i `glab`.[^4][^3][^1][^5]

Najkrótszy opis projektu można sformułować tak:

> `tagi` to paczka Python i narzędzie CLI do orkiestracji wysyłek zmian Git. Analizuje nie wysłane pliki, grupuje je hashtagami, buduje sensowne paczki commitów i bezpiecznie uruchamia workflow publikacji przy użyciu istniejących narzędzi Git, GitHub CLI i GitLab CLI.[^2][^3][^4][^1]
