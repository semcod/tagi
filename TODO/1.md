# tagi powinien być bardziej orchestratorem wysyłek niż zastępować komende git

Tak — to lepszy kierunek. **tagi** powinien być warstwą orkiestracji nad Git, a nie zamiennikiem samego Gita; Git ma pozostać silnikiem wykonawczym, a `tagi` ma pomagać podjąć decyzję, co wysłać i jak to opisać.[^1][^2]

## Rola tagi

Najzdrowszy model to: Git zostaje od operacji typu `status`, `add`, `commit`, `push`, a **tagi** robi analizę, grupowanie, planowanie i bezpieczne odpalanie sekwencji działań. To jest zgodne z ideą CLI jako warstwy wyższego poziomu nad istniejącymi komendami oraz z gitowym podziałem na warstwę user-facing i warstwę narzędziową.[^3][^2][^1]

Czyli:

- Git = wykonanie.
- `tagi` = selekcja, heurystyki, sugestie, orkiestracja.
- `gh` / `glab` = auth i integracja z hostingiem.[^4][^5]


## Dobry model działania

`tagi` nie powinien mieć ambicji „być nowym gitem”, tylko prowadzić usera przez workflow wysyłki zmian. Najlepiej, żeby kończył się on na jawnych, przewidywalnych krokach, np. preview → confirm → execute, zamiast ukrywać operacje Git pod zbyt magicznym interfejsem.[^6][^3]

Dobrze brzmi taki flow:

1. `tagi scan` — czyta repo i wykrywa grupy zmian.
2. `tagi plan` — pokazuje paczki i hashtagowe kategorie.
3. `tagi send #small` — proponuje staging, commit message i push plan.
4. `tagi apply #small --commit --push` — wykonuje wyłącznie wybraną orkiestrację.[^7]

## Co powinno robić

Jako orchestrator, `tagi` powinien:

- analizować `git status --porcelain` i diffy;
- budować grupy plików na podstawie heurystyk;
- proponować paczki wysyłkowe;
- pokazywać skutki akcji przed wykonaniem;
- generować opis commita i opcjonalnie PR/MR;
- odpalać Git i `gh`/`glab` tylko na końcu, po decyzji usera.[^8][^5][^4]

To znaczy, że komendy typu `git add`, `git commit`, `git push` nadal istnieją i nadal są podstawowe; `tagi` jedynie składa je w scenariusze.[^2][^1]

## Czego nie powinno robić

Nie polecałbym, żeby `tagi`:

- implementował własny staging model zamiast `git add`;
- trzymał własny stan repo niezależnie od `.git`;
- ukrywał, jakie dokładnie komendy wykona;
- zmieniał semantykę commita lub pusha względem Git;
- próbował zastąpić branching, rebasing albo merge workflow.[^1][^2]

Innymi słowy: ma być **orchestrator wysyłek**, nie „Git 2.0”.[^3][^1]

## Proponowany zakres

Najbardziej sensowny zakres produktu to trzy poziomy:


| Poziom | Odpowiedzialność | Narzędzia |
| :-- | :-- | :-- |
| Analiza | `git status`, diff stats, tagi, ryzyko | `git`, Python, heurystyki [^7] |
| Decyzja | wybór paczki, preview, opis, priorytet | `tagi`, `rich`, `typer` [^3] |
| Wysłanie | stage, commit, push, opcjonalnie PR/MR | `git`, `gh`, `glab` [^4][^5] |

To rozdzielenie jest ważne, bo utrzymuje prosty model mentalny: `tagi` decyduje **jaką paczkę wysłać**, a Git/hosting decydują **jak technicznie ją wykonać**.[^2][^3]

## Komendy

Zamiast kopiować strukturę Gita, lepiej nadać komendom charakter operacyjny:

- `tagi scan` — wykryj zmiany i tagi.
- `tagi list` — pokaż paczki.
- `tagi inspect #small` — pokaż, co jest w grupie.
- `tagi draft #small` — przygotuj opis i plan wysyłki.
- `tagi send #small` — staging + commit + opcjonalny push.
- `tagi publish #small` — także PR/MR, jeśli provider dostępny.[^5][^4][^3]

To sprawia, że `tagi` brzmi jak orchestrator zadań, a nie wrapper 1:1 na `git commit` czy `git push`.[^3]

## Architektura

W tej wersji architektura powinna być bardziej workflow-driven niż Git-driven:

- `scanner` — czyta stan repo;
- `classifier` — przypisuje tagi;
- `planner` — buduje paczki wysyłkowe;
- `composer` — generuje opis;
- `executor` — odpala konkretne komendy `git`, `gh`, `glab`;
- `providers` — GitHub/GitLab/enterprise;
- `llm` — poprawia komunikaty, ale nie steruje logiką wysyłki.[^9][^4][^5]

Tu szczególnie ważne jest, żeby `executor` był cienką warstwą nad realnymi komendami, np.:

- `git add file1 file2`
- `git commit -m "..."`
- `git push origin branch`
- `gh pr create` albo odpowiednik GitLab.[^4][^5]


## Definicja produktu

Jednym zdaniem opisałbym projekt tak:

**tagi to CLI do orkiestracji wysyłek zmian Git — analizuje nie wysłane pliki, grupuje je hashtagami, proponuje sensowne paczki commita i uruchamia istniejące narzędzia Git/GitHub/GitLab do ich publikacji.**[^5][^7][^4]

To pozycjonowanie jest dużo lepsze niż „narzędzie zastępujące Git”, bo jest prostsze do zrozumienia, bezpieczniejsze i bardziej rozszerzalne.[^6][^3]

Następny sensowny krok to spisać to jako **manifest produktu + listę komend MVP**, żeby od razu ustawić granice projektu.
